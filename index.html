How to use this guide

A slow read-through of the Angular project you just generated, built from your actual files, with the review questions from step 0.3 and their answers.

  • Read a chapter, then tick it. Your progress is saved in this browser only.
  • In the questions chapter, write your own answer first. Then reveal the model answer and mark yourself "Got it" or "Review again". Predicting before checking is how this sticks.
  • Everything here refers to real files in ~/code-projects/angular-kanban. Open them beside this page.
Two things I verified, so you can trust them The project has no zone.js (it is zoneless), and TypeScript strict mode is effectively on even though tsconfig.json never says "strict": true. I proved the second one by adding const s: string | null = null; s.length; to app.ts: the build failed with TS18047: 's' is possibly 'null'. I reverted the edit afterwards.

    Chapter 4 · Question 2
    
  
    Where would things go?
    
  
    Two questions you will answer for real in Milestones 2, 3 and 6. Here is the map.
    

  
    A global service (one shared instance)
    
  
    Most of the time, you do not register it anywhere. Put @Injectable({ providedIn: 'root' }) on the class, and Angular creates a single shared instance the first time something asks for it with inject(). That is what you will do for the board store in step 2.1.
    
  
    You register something explicitly in appConfig.providers (src/app/app.config.ts) when it is not providedIn: 'root':
    
  
      
    
    • Provider functions that switch on a capability: provideHttpClient() (step 3.4), provideRouter(routes) (step 6.1).
      • 
    
    • Configuration values through an InjectionToken.
      • 
    
    • Choosing an implementation, for example a fake API in tests and a real one in production.
      • 
  
    
  
    
  
    Your appConfig already has one provider, provideBrowserGlobalErrorListeners(). More on why it matters in chapter 5.
    

  
    A route
    
  
    Routes are plain data: an array of Routes, conventionally in a new file src/app/app.routes.ts. Three things connect them to the app:
    
  
      
    
    1. Export the array: export const routes: Routes = [ ... ]
      2. 
    
    2. Add provideRouter(routes) to appConfig.providers.
      3. 
    
    3. Put <router-outlet /> in a template (the root component imports RouterOutlet). The outlet is where the matched component appears.
      4. 
  
    
  
    Right now there are no routes
    You created the project with --routing=false, so there is no app.routes.ts and no provideRouter. Notice that @angular/router is still installed (see package.json). The package is there; the feature is not switched on. You do this in step 6.1.
  
    
  
    

    



    
  
    Chapter 5 · Question 3
    
  
    How does Angular know when to re-render?
    
  
    There is no zone.js in your package.json. Older Angular used it to notice that anything asynchronous happened (a click, a timer, a network response) and then checked the whole tree. Your app does not do that.
    

  
    Angular now waits to be told
    
  
    In a zoneless app, a re-render is scheduled when something explicitly signals a change. The main signals:
    
  
    
    
    TriggerExample in your project
    
    
      
    A signal read by a template changesapp.html reads title(). Calling title.set('x') updates that text, and only that.
    
      
    A template event listener runs(click)="..." on a button
    
      
    ChangeDetectorRef.markForCheck() is calledThe async pipe does this for you when an observable emits
    
      
    An input is set on a componentA parent binding changes a child's input()
    
      
    A view is attached or removed@if and @for adding or removing content
    
        
  
    

  
    What does not trigger a render
    Changing an ordinary class field inside a setTimeout, a promise, a fetch callback or an RxJS subscribe. Nothing tells Angular, so the screen stays stale. This is why this project keeps its state in signals, and why Milestone 2 starts there.
  
    

  
    Try it (5 minutes, then revert with git restore)
    
  
      
    
    1. In app.ts, add to the class: constructor() { setTimeout(() => this.title.set('changed'), 2000); }. Expected: after two seconds the heading changes to "Hello, changed", with no other code.
      2. 
    
    2. Revert. Now add a plain field protected name = 'a';, show {{ name }} in the template, and change it in a setTimeout. Expected: the page does not update.
      3. 
    
    3. If either result differs from what I wrote, that is a great thing to bring to your review.
      4. 
  
    

  
    Why provideBrowserGlobalErrorListeners() is in your config
    
  
    It forwards uncaught browser errors (window error and unhandled promise rejections) to Angular's ErrorHandler. Zone.js used to be what noticed those errors for Angular. Without zones, this provider is how they still get reported.
